## INFO (documented, backlogged)

### INFO-A: Lazy-global allocs still abort on first-call OOM

**Files**: `src/lz77.cyr` (`lz77_init`), `src/huffman.cyr`
(`_huff_alloc_tables`, `_huff_fixed_litlen_lens`, `_hcl_ws`),
`src/deflate.cyr` (`_deflate_*_lookup` builders, `_dh_ws`,
`_dyn_*` workspace builders), `src/lz4.cyr` (`_lz4_htab` init),
`src/checksum.cyr` (`crc32_table`).

**Status**: Carried forward from 2.2.1's CHANGELOG. The 2.2.1
defensive-alloc work covered the `*_enc_init` entry-point surface
(6 alloc sites) but explicitly deferred the 35 lazy-global sites.
Failure mode: a first-call OOM during one of these helpers leaves
the lazy global at 0; the next read does
`store64(0 + h * 8, ...)` → segfault, with `_sankoch_mtx` held
because the entry point that called the helper is still inside
its locked region.

**Why deferred**: each lazy global is reachable from many internal
callers; propagating an alloc-failure error would mean adding
return-value checks at every callsite plus an error-bearing entry
in the helper signatures. The lazy globals are also init-once-
per-process — in a process that successfully allocates them on
first call, no subsequent OOM is possible. The realistic OOM
victim is the per-call ctx alloc, which 2.2.1 hardened.

**Decision**: keep deferred. Revisit if a consumer shows up that
runs sankoch under tight memory pressure with a fresh process per
call (no warm globals).

### INFO-B: `_deflate_decompress_dict` requires `dst_cap >= dict_len`

**File**: `src/deflate.cyr` — `_deflate_decompress_dict_inner`
(line ~419-440).

**Behavior**: The dict-aware decoder stages the dictionary into
`dst[0..dict_len]` before decoding the DEFLATE payload, then moves
the decoded output back to `dst[0..]` via byte-by-byte copy. If
`dst_cap < dict_len`, the early check
`if (dict_len > dst_cap) { return -ERR_BUFFER_TOO_SMALL; }` (line
420) rejects the call with a proper error — no UB.

**Surfaced via**: a too-tight `var out = alloc(64)` in the
audit-driven `test_enc_dict_max_len_32768` test, where the
correct ERR_BUFFER_TOO_SMALL return was misread as a round-trip
correctness failure. Test fixed in 2.2.3 (uses `alloc(65536)`).

**Action**: docstring on `deflate_decompress_dict` and
`zlib_decompress_dict` could call this constraint out more
prominently (currently implicit in the error-path code). Marked
as a future docs-polish item; not changing API behavior.

### INFO-C: aarch64 LZ77 8-byte word-compare uses unaligned loads

**File**: `src/lz77.cyr` — `_lz77_find_match` (line ~110-115).

**Behavior**: The match-extend hot loop does
`var a = load64(src + chain_off + mlen); var b = load64(src + win_pos + mlen);`
with no alignment guarantee on either operand. ARMv6+ permits
unaligned 8-byte loads, but some ARM implementations take a
performance penalty (extra cycles for unaligned access vs
aligned). x86 has no such penalty — the speed-up the 2.1.0
match-extend rewrite measured was on x86.

**Action**: documented for future investigation. If aarch64 perf
benchmarks land and this section dominates, an alignment-aware
variant (run a byte-prefix loop until `(src + chain_off + mlen) %
8 == 0`, then word-compare) is a candidate. Holding pattern: no
consumer signal yet.
