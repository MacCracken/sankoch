## TL;DR

This is the opposite of the previous pass. The 2.3.x closeout recorded **zero** findings; the 2.4.x/2.5.x arcs added ~5,700 lines of never-audited codec code, and it shows.

**Confirmed, post-verification: 1 HIGH · 13 MEDIUM · 5 LOW · 1 new INFO.** Eleven further reports were **refuted or severity-rebased downward** (six MEDIUM/HIGH claims that survived reproduction but not the severity bar, five that collapsed on inspection). Every confirmed finding was reproduced by execution unless explicitly labelled inferred, and every one carries a verified patch.

The findings collapse into **six root causes**, none of which the green CI gates can see:

1. **OOM propagation is broken across the never-audited encoders** — this is the direct, negative answer to INFO-E. Four lazy-init blocks guard on the wrong pointer, so a partial first-call OOM latches and the *next* call writes through a NULL table (`lz77_init`, `_bze_alloc`, the xz encoder DP block, the three zstd `_ze_*_alloc`). Reachable from `deflate/zlib/gzip/xz/bzip2/zstd` compress. **1 HIGH-adjacent class, verified MEDIUM.**
2. **The bump arena never frees, so several hot paths leak unbounded per call** (`zstd_decompress` 262 KB/call; the zstd encoder's per-block FSE ctables; `tar_open_auto`'s futile retry ladder ~1 GiB/call). Amplifies INFO-D from "orphans memory on retry" to a real resource-exhaustion DoS.
3. **`tar_open_auto` sizes and retries on attacker-controlled fields** (ERR_OUTPUT_LIMIT treated as growable; forged gzip ISIZE; unchecked >2 GiB parse-field allocs).
4. **xz container-layer input validation gaps** (check-field read *before* its bound; unbounded Index-record loop hanging under the API mutex; `--check=sha256` accepted with zero payload verification).
5. **`src/zstd.cyr` takes no mutex at all** while owning 49 per-call globals — a documented-invariant violation that materialises as corruption + SIGSEGV under concurrent callers.
6. **Correctness/interop:** multi-frame `.zst` silently truncated to frame 1; valid multi-member `.tar.gz` wrongly rejected.

**The single HIGH is a symlink-chain path traversal in the tar cursor** (arbitrary file write outside the extraction root, silent, from a downloaded tarball). It has a verified fix but that fix is **not yet landed at `e99ba4d`**.

**Verdict: NOT cleared to open 2.6.0 at HEAD.** The HIGH and the public-API-reachable MEDIUMs must land first (verified patches ready; see Remediation). This is a remediation-then-reclear, not a redesign.

## Confirmed findings

Severity = verifier's judgment. Every location is against `e99ba4d`.

### HIGH

#### H-1 — Symlink-chain traversal: relative symlinks escape the extraction root
- **Location:** `src/tar.cyr:154-200` (`_star_symlink_safe`), gate applied at `src/tar.cyr:413`/`:426`.
- **Severity:** HIGH (confirmed; reproduced from scratch).
- **Trigger:** A four-entry archive of purely *relative* entries — `d/` (dir), `d/up → ..` (symlink), `esc → d/up/..` (symlink), then a plain file `esc/pwned.txt`. `_star_symlink_safe` computes link depth per-entry, charging +1 for each ordinary target component; that is only correct if intermediate components are real directories. An earlier symlinked component makes the arithmetic wrong, the effective depth goes negative, and the cursor — which keeps no cross-entry state — blesses the later file whose own path contains no `..`. `tar_next` returns 1 for every entry, 0 at the end, no error.
- **Proof:** The repo's own `programs/tar_smoke.cyr` extractor, `OUT_DIR=/tmp/sankoch-tar-out`, exits 0 and writes the payload to `/tmp/pwned.txt` — one level **above** the extraction root. GNU tar 1.35 on the identical bytes refuses (`Cannot open: Not a directory`, rc=2). A randomized differential (3,000 archives) found two more escapes of the same class the shipped guard accepts (`lib → .` then `b → lib/..`; and a three-hop variant). The single-hop guard is correct; the hole is strictly the multi-hop chain and the write-through of an absolute-target link.
- **Reachability:** Public API (`tar_next`) on fully attacker-controlled input — a downloaded source tarball, which is exactly the `[lib.tar]` charter (takumi/agnova). Silent (rc 0, no `TAR_ERR`). The module docstring at `src/tar.cyr:6-8` claims traversal safety is "enforced HERE, so every consumer inherits the guards for free" — an overclaim until the fix lands.
- **Verified fix:** Add a **resolving symlink ledger** to the 128-byte cursor (previously-unused slot +24): record every emitted symlink's normalised path together with its target *already resolved* to a root-relative form, indexed by a 1024-bucket FNV-1a hash. Resolve each subsequent entry's directory prefix through the ledger and reject with `TAR_ERR_UNSAFE` only when resolution actually leaves the root or crosses an absolute-target (opaque) link. Resolving-not-blanket-rejecting is load-bearing: it preserves the benign `lib → usr/lib` + `lib/foo.so` merged-/usr shape that GNU tar accepts (agnova's workload). The auditor's originally-proposed byte-prefix fix was **proven defective** (a single `./` defeats it; it over-rejects the benign case; it leaves the poisoning link live on disk) and must not be used. The naive linear-scan ledger is an O(N²) CPU bomb on N symlinks + N deep paths — the hash index is required, not optional.
- **Residual (any fix of this shape):** The ledger only knows symlinks *this archive* planted; a pre-existing symlink in the destination is still invisible. The docstring must be corrected regardless, and consumers should still extract with `openat2(RESOLVE_BENEATH)`/`O_NOFOLLOW` per component — the cursor guard is defence in depth, not a substitute. Notify takumi/agnova.

### MEDIUM

#### M-1 — `tar_open_auto` treats ERR_OUTPUT_LIMIT as growable, burning ~1 GiB of never-freed arena per hostile stream
- **Location:** `src/tar.cyr:492-511` (retry predicate at `:504`); sibling one-shot at `src/tar.cyr:480-490` (gzip ISIZE).
- **Trigger:** Any `.xz`/`.bz2` decoding to >16 MiB (e.g. `bzip2 -9 </dev/zero` truncated to 49 bytes). `ERR_OUTPUT_LIMIT` is the codec's fixed 16 MiB `DECOMPRESS_MAX_OUTPUT` ceiling, independent of `cap`; the ladder doubles anyway from 1 MiB to 512 MiB, re-running a full 16 MiB decode on each rung and bumping ~1,072,693,248 bytes (= 1023 MiB) of arena that never frees. Measured: 49-byte input → 1.07 GB arena, 114 MB RSS, ~0.34 s; five calls on the same file → 5.1 GB arena / 558 MB RSS.
- **Proof:** Per-rung log shows rungs 1–5 legitimately return `ERR_BUFFER_TOO_SMALL` (real growth); rungs 6–10 return `ERR_OUTPUT_LIMIT` (992 MiB of provably-futile allocation). All four `ERR_OUTPUT_LIMIT` emission sites test `dst_cap` *before* the ceiling, so an `ERR_OUTPUT_LIMIT` return *proves* `cap` already exceeded 16 MiB — growing can never change the outcome.
- **Verified fix:** Drop `ERR_OUTPUT_LIMIT` from the retry predicate (only `ERR_BUFFER_TOO_SMALL` is growable) **and** clamp the ladder ceiling to `min(TAR_MAX_OUT, DECOMPRESS_MAX_OUTPUT)`. Both halves needed: predicate-change alone reaches ~63 MB/6 passes, not one pass; the clamp brings it to 31 MB/5 passes. Verified outcome-preserving on 14 archives incl. the exact-16-MiB boundary case. Also close the gzip sibling: reject a forged ISIZE above `DECOMPRESS_MAX_OUTPUT` *before* allocating (a 20-byte gzip with ISIZE=512 MiB otherwise bumps 512 MiB, higher per-byte amplification than the ladder).

#### M-2 — Multi-frame `.zst` silently truncated to the first frame
- **Location:** `src/tar.cyr:468-478` (sizing via `zstd_frame_content_size`); root cause `src/zstd.cyr:713-808` (`zstd_decompress` decodes exactly one frame, returns success, ignores trailing frames).
- **Trigger:** A concatenated multi-frame `.zst` (`split` → per-part `zstd -q -c` → concat; `cat a.zst b.zst`; multi-frame producers). RFC 8878 §3 defines a `.zst` file as a concatenation of frames; sankoch's own gzip/xz/bzip2 decoders handle concatenation, zstd was the outlier and the limitation was undocumented (unlike lz4, which documents "single-frame only").
- **Proof:** 3-frame 16.3 MB archive → reference `zstd -dc` yields 21,657,600 bytes / 41 entries; sankoch `zstd_decompress` returns 8,000,000 (frame 1) as **success**, `tar_open_auto` hands back a non-NULL cursor over the truncated archive (`ENTRIES=15 ENDR=-2`). Reachable from `zstd_decompress`, `decompress(FORMAT_ZSTD,…)`, and `tar_open_auto`. Two supporting sub-claims in the original report were refuted: pzstd input fails *loud* (skippable-frame prefix isn't sniffed), and `cat` of two complete tar archives is not a divergence (GNU tar also stops at the first end-of-archive marker) — the genuine silent case needs a single logical stream cut mid-stream across frames.
- **Verified fix:** Add a concatenated-frame loop to `zstd_decompress` (skippable-frame magic `0x184D2A5x` skipped by its length; Zstandard-frame magic `0x28B52FFD` continues into `dst` at the current offset), and switch tar sizing to a whole-stream `zstd_content_size`. Deliberately reset `_z_lit` once per call (not per frame — per-frame would re-leak 256 KiB/frame; see M-9); reset the true per-frame state (repcodes, Huffman/FSE repeat tables) inside the loop. Loop-progress guards prevent zero-advance/OOB on hostile skippable lengths. No wire-format/perf change; byte-exact vs `zstd -dc` on multi/skippable/single-frame inputs.

#### M-3 — Unchecked allocations on the tar parse path → NULL-page write; reachable via a >2 GiB archive
- **Location:** `src/tar.cyr:71, :84, :240, :257, :335` (parse-path allocs, unchecked). (`:473/:486/:498` in the decompress path *are* checked.)
- **Trigger:** A single tar field whose length exceeds `ALLOC_MAX` (2 GiB) makes `alloc()` return 0 on the pure size check, and the next `memcpy(buf,…)`/`store64(r+0,…)` faults on the null page. Concretely proven: a 2 GiB GNU LongLink ('L') entry with a >2 GiB NUL-free linkname drives `_star_field_cstr` to `alloc(0x80000001)` → 0 → `memcpy(0,…,2GiB)` → SIGSEGV, reached through the public `tar_open`/`tar_next`. `tar_open_auto` applies its `TAR_MAX_OUT` ceiling only to *compressed* inputs; a plain tar falls straight through with no cap.
- **Proof:** Purpose-built 2 GiB archive → rc 139 pre-fix, clean `-7` (`TAR_ERR_OOM`) post-fix. Of the five sites, two (`_star_field_cstr` via 'L'/'K', `_star_pax_cstr` via a PAX `path=` record) are triggerable with a constructible >2 GiB input; three need genuine exhaustion. **Resolves INFO-E for tar: not covered, and structurally uncoverable** — tar bypassed the `_sankoch_alloc` fault-injection seam entirely (0/400 injected faults diverged pre-fix vs 19/400 post-fix).
- **Verified fix:** Route all 8 tar allocs through `_sankoch_alloc`; add a 0-check to each of the 5 parse-path sites; add `TAR_ERR_OOM = 7`; `tar_next` maps a 0 return to `-TAR_ERR_OOM`. `[lib.tar]` already carries `runtime.cyr`, so no manifest change.

#### M-4 — `tar_open_auto` rejects a valid multi-member `.tar.gz` its own decoder handles
- **Location:** `src/tar.cyr:480-490` (gzip branch); sizing helper `_star_gzip_isize` at `src/tar.cyr:~233`.
- **Trigger:** A concatenated multi-member gzip stream (pigz, `cat a.gz b.gz`, split-then-gzip). `_star_gzip_isize` reads only the last 4 bytes — the ISIZE of the *final* member — so the buffer is under-sized, `gzip_decompress` returns `ERR_BUFFER_TOO_SMALL`, and the gzip branch (unlike the xz/bzip2 branch below it) has no retry, returning 0.
- **Proof:** A genuine 2-member `.tar.gz` (10,240-byte tar) that `gunzip -c | cmp` and `tar -tf` both accept: `gzip_decompress` into 1 MiB returns 10240 (full, both members), but `tar_open_auto` returns 0. This is a **fail-safe interop bug** (returns "could not open," never wrong data, never a crash) — closer to LOW on exploitability, MEDIUM as a functional defect reachable on legitimate input. The claimed ≥4 GiB single-member ISIZE-wrap sub-case is **moot** (the 512 MiB `TAR_MAX_OUT` ceiling rejects it first).
- **Verified fix:** Merge the gzip branch into the shared xz/bzip2 retry loop, seeding `cap` from ISIZE as a *hint* (floor only un-hinted guesses to 1 MiB, so the common single-member case still allocates once from the arena).

#### M-5 — xz block check field is read before its bounds check → up to 8-byte OOB read
- **Location:** `src/xz.cyr:513` (CRC-32, 4 bytes) and `src/xz.cyr:520-521` (CRC-64, 8 bytes), inside `_xz_verify_check`; the length guard that should precede them is at `src/xz.cyr:591` (caller side, *after* the call at `:589`).
- **Trigger:** Any valid `.xz` with `check=CRC32|CRC64` truncated to the offset where a block's check field begins (or 1..7 bytes into it). `_xz_verify_check` does `_xz_le32(at)` before any bound is applied.
- **Proof:** Guard-page probe: exhaustive truncation sweep SIGSEGVs at exactly 4 prefixes for a CRC-32 file, exactly 8 for CRC-64, and 0 for `check=none`/`check=sha256` — matching the mechanism precisely. In the ordinary heap case the read grabs adjacent bytes and returns a spurious `ERR_CHECKSUM_MISMATCH`. Reachable from `xz_decompress`, `xz_decompress_with_ratio_cap`, `decompress(FORMAT_XZ)`, `tar_open_auto`.
- **Verified fix:** Bound-check before reading — `if (at + 4 > _xz_in_end)` / `if (at + 8 > _xz_in_end)` / `if (at + 32 > _xz_in_end)` at the top of each branch; return `ERR_CORRUPT_DATA`. Decode-only, local to `xz.cyr`. (This is the substance behind the "fuzz_xz has no truncation strategy" LOW report — the harness gap is real but secondary; see L-5.)

#### M-6 — Unbounded Index-record loop: a 66-byte crafted `.xz` hangs forever holding `_sankoch_mtx`
- **Location:** `src/xz.cyr:637` (raw varint read) and `src/xz.cyr:640-644` (loop).
- **Trigger:** An Index whose Number-of-Records is a 9-byte varint up to ~2⁶². `_xz_varint` sets a sticky `_xz_err` and returns 0 without advancing once past `_xz_in_end`, so the loop body becomes a no-op the loop repeats for an attacker-chosen count; `_xz_err` is only checked *after* the loop. `xz_decompress` holds `_sankoch_mtx` throughout, so the spin blocks every other sankoch thread — a full-library deadlock, not a slow call.
- **Proof:** 66-byte `i56.xz` (num_records = 2⁵⁶) → `build/xzguard` still spinning past a 15 s timeout (rc 124); reference `xz -dc` rejects instantly. Linear at ~5.5 ns/record (2⁵⁶ ≈ 12 years).
- **Verified fix:** Two guards — reject up front (every record is ≥2 bytes, so `num_records > (in_end - in_pos)/2` is impossible), and break on `_xz_err` inside the loop body. Decode-only; a legitimate 13-record index still decodes.

#### M-7 — `--check=sha256` payloads accepted with zero integrity verification (silent corruption)
- **Location:** `src/xz.cyr:526` (`if (check_type == 10) { return 32; }`); misleading claim at `src/xz.cyr:9-13`.
- **Trigger:** A `.xz` produced with `xz --check=sha256` whose LZMA2 payload is tampered but still decodes structurally. The 32-byte digest is skipped entirely (no SHA-256 primitive in the tree); the per-block header CRC-32 covers only the 8-byte header, not one payload byte.
- **Proof:** Flipping one payload byte of a sha256-checked stream → reference `xz -dc` rejects (`Compressed data is corrupt`); sankoch returns success with wrong plaintext. Controls confirm CRC-32/CRC-64 streams *are* caught. Bounded impact: only the rare sha256 mode is affected (sankoch's own encoder emits CRC-64), and an attacker controlling the whole stream gains nothing over crafting plaintext directly — the real harm is undetected accidental/transit corruption of a legitimately protected stream.
- **Verified fix (fail-closed):** `if (check_type == 10) { return 0 - ERR_UNSUPPORTED_FORMAT; }` plus corrected header comment. Behaviour change for a valid-but-rare container — **needs a CHANGELOG note.** Wire-preserving alternative: inline SHA-256 in `xz.cyr` (keeps `[lib.xz]` self-contained) so valid sha256 streams still decode while corruption is caught — deferred to its own arc.

#### M-8 — Sticky partial lazy-init OOM: an ERR_OOM returns cleanly, then the next call writes through a NULL table
- **Location:** `src/lz77.cyr:167` (`lz77_init`, guards on `_lz77_head` only, allocates two 256 KB buffers); `src/bzip2.cyr:579` (`_bze_alloc`, guards on `_bze_rle` — the first of 21 allocs); `src/xz.cyr:1698` (the `_xze_prices` DP block, 15 allocs checked only collectively after); `src/zstd.cyr:886/1287/1779` (`_ze_huff_alloc`/`_ze_lz_alloc`/`_ze_seq_plan_alloc`, which check **no** alloc result at all).
- **Trigger:** One allocation failure inside the lazy init, followed by a retry (the documented reaction to `-ERR_OOM`). The guard pointer is already set, so the retry skips the whole block and dereferences a still-NULL sibling. `lz77_init` is shared, so this hits `deflate/zlib/gzip/xz` compress; the encoders hit `bzip2`/`zstd`/`xz` compress.
- **Proof:** Both fault injection (`_sankoch_alloc_set_fail_at`) *and* real allocator failure with no test hook (`ulimit -v` + arena burn) reproduce SIGSEGV on the retry — e.g. `lz77_init` core dump: `si_addr=0x0`, `rax=0xffffffffffffffff` = `store64(_lz77_prev + 0*8, -1)`. The zstd encoder additionally crashes on the *first* call under real OOM (unchecked allocs), and after the standard fix a residual ~18 KB heap-headroom window still SIGSEGVs at `_ze_fse_ctable` (`src/zstd.cyr:1608`) and `_z_fse_alloc`.
- **Severity note:** Verified MEDIUM, not HIGH — the trigger is allocator state, not attacker-controlled input; alloc sizes are input-independent; and the write is a deterministic NULL-page fault (crash/DoS), not a steerable primitive (page 0 unmapped, all sites decode-side-free / not in `[lib.core]`). What lifts it above LOW: the latch is **permanent** — one partial OOM kills every subsequent compress in the process.
- **Verified fix:** Replace the pointer-sentinel with a dedicated `_*_allocd` completion flag set only after the all-non-zero check, and zero the group (or the guard) on failure so a retry re-enters cleanly (orphaning the partial allocation in the never-freeing arena = accepted INFO-D, strictly better than a wild write). Applied to `lz77_init`, `_bze_alloc`, the xz DP block; zstd gets per-alloc null checks + a sticky `_ze_oom` flag + caller bail-outs. **zstd remains only partially closed** — the `_ze_fse_ctable`/`_z_fse_alloc` per-call sites need the same treatment (see Remediation). **This is the negative answer to INFO-E.**

#### M-9 — `zstd_decompress` permanently leaks ~262 KB of arena per call
- **Location:** `src/zstd.cyr:720` (`_z_lit = 0` in the per-call reset), defeating the `if (_z_lit == 0) { _z_lit = alloc(1 << 18); }` cache at `src/zstd.cyr:457/:492`.
- **Trigger:** Any valid frame with a literals section, decoded more than once. `_z_lit` is a fixed 256 KiB scratch fully rewritten before it is read, but zeroing the guard forces a fresh `alloc(1<<18)` each call; the bump arena never frees.
- **Proof:** 267,064 B/call measured over 1000 warm calls (vs 0–32 B/call for every other codec) through `decompress(FORMAT_ZSTD,…)`. 4,000 frames ≈ 1 GB. Highly-compressible input takes the RLE path and doesn't leak (needs a real Compressed_Block, i.e. any realistic data).
- **Severity note:** Verified MEDIUM (resource-exhaustion DoS; output always byte-correct), not the reported HIGH.
- **Verified fix:** Drop `_z_lit` from the per-call reset (one line). Leak → 0 B/call incremental for `_z_lit`; a smaller residual (~4.9 KB/call: per-block FSE-table backing arrays + 40-byte bit-reader structs) remains and needs the persistent-global conversion as a careful follow-up — the seq FSE tables carry Repeat-mode cross-block state, so shared-buffer caching must not silently change table reuse.

#### M-10 — zstd encoder leaks FSE coding tables every block and null-derefs on the resulting OOM
- **Location:** `src/zstd.cyr:1566` (`_ze_fse_ctable`) + sub-allocs at `:1570/:1581/:1590/:1591/:1610` and `_z_fse_alloc` `:252/:255`, `_z_fse_build` `:205`; per-block call sites `:1751/:1848/:1865`.
- **Trigger:** Any long-lived process calling `zstd_compress` repeatedly on ordinary structured input (ark packaging daemon, container writers). Each block re-allocates fresh FSE encode tables via raw `alloc()`, never cached, never freed. Measured ~18–23 KB/ctable/block, dead-flat linear growth (the *predefined* `_ze_ct_ll/of/ml` tables *are* cached — only the adaptive + Huffman-weight paths leak). On eventual `alloc()==0`, unchecked `store64` faults on the null page.
- **Proof:** ~23 KB/call steady-state → 33 MB over 4000 iters; OOM probe SIGSEGVs at the unchecked store.
- **Verified fix:** Pool the FSE ctable working buffers into lazily-allocated, reused, slot-indexed globals (≤3 sequence ctables + 1 weight ctable live per block, consumed sequentially); add null-checks that set `_ze_err` and bail before any NULL use. Leak → 0 B/call; wire format byte-identical (SHA-256 match, round-trips via `zstd -d`). Do **not** route through `_sankoch_alloc` — `[lib.zstd]` is `types.cyr + zstd.cyr` only.

#### M-11 — `zstd_decompress` SIGSEGVs on a valid frame under heap exhaustion (unchecked decode-path allocs)
- **Location:** `src/zstd.cyr:457` and `:493` (`_z_lit`), plus every other unchecked decode-path alloc: `_z_br_init` `:134`, `_z_flr_init` `:170`, `_z_fse_build` `:205`, `_z_fse_alloc` `:252-257`, `_z_huff_build` `:271`, `_z_huff_tree` `:301/:322-324`, `_z_seq_table` `:679`.
- **Trigger:** Decoding any frame with a literals section while the allocator cannot satisfy a request (container memory cap, `RLIMIT_AS`, fragmented VA, or — with no external limit at all — after the M-9 leak exhausts the arena). `alloc()` returns 0 and the following `store` hits the null page. Note this is reachable *purely from repeated valid public-API calls* via the M-9 leak.
- **Proof:** `RLIMIT_AS` + descending burn to a 256 KiB floor → exit 139, core dump `mov %al,(%rcx)` rcx=0. The auditor's own "unproved residual" was **proven**: the 2-line `_z_lit`-only fix leaves a ~256–274 KiB slack window that still SIGSEGVs at a later alloc.
- **Verified fix:** Null-check **every** decode-path alloc site (not just `_z_lit`), returning the appropriate negative error; the existing `llt/oft/mlt == 0 → -53` guards catch propagated zeros. Extended fix returns clean `-47/-53/-71/-72` across the whole window; wire format preserved both directions vs zstd 1.5.7.

#### M-12 — `src/zstd.cyr` takes no mutex while mutating 49 per-call globals → concurrent corruption + SIGSEGV
- **Location:** `src/zstd.cyr` (0 occurrences of `_sankoch_lock`); public entries `zstd_decompress` `:713`, `zstd_compress`/`zstd_compress_level` `:2048/:2062`, `zstd_set_level` `:1236`. Contradicts `docs/architecture/README.md:33` and CLAUDE.md § Key Constraints. Reached unlocked via `src/tar.cyr:475`.
- **Trigger:** Two threads calling `zstd_decompress` (or the generic `decompress(FORMAT_ZSTD,…)` alongside a direct `zstd_*` call) concurrently. `_z_out/_z_outpos/_z_outcap`, the recent-offset triple, and lazily-allocated table pointers race.
- **Proof:** Two-thread probe (each looping 4000× over its own reference-CLI frame into its own buffer): sequential = 0 failures; concurrent = **20/20 runs failed — 11 wrong-output, 9 hard SIGSEGV** (interleaved `_z_outpos` publishing makes the `_z_outpos + n > _z_outcap` guards validate against the wrong buffer's capacity → genuine OOB write). A control that routes through the locked `decompress()` dispatch is clean.
- **Severity note:** Verified MEDIUM — attacker controls the bytes but not the concurrency; single-threaded consumers unaffected. But the library *promises* serialization and every other codec delivers it.
- **Verified fix:** Add `src/runtime.cyr` to `[lib.zstd]` in `cyrius.cyml` (mirrors `[lib.zlib]/[gzip]/[xz]/[bzip2]`, +88 lines, keeps the profile stdlib-only) and wrap the four public entries in `_sankoch_lock/_unlock` over new `_zstd_*_inner` bodies; repoint `lib.cyr`'s `_compress_inner`/`_decompress_inner` at the inners (no recursive-lock). The originally-proposed "route tar through `decompress()`" fix was **proven broken** (undefined symbol in the `[lib.tar]` closure, silently past the dist gate). Promote the "AGNOS userland is single-threaded" assumption (which makes the no-op lock sound) from a code comment to a numbered `docs/architecture/` item.

#### M-13 — `stream_write` / `stream_*_init` never check `alloc()` → NULL-page write
- **Location:** `src/stream.cyr:88` (`_stream_grow`), `:181-189` (buffered `stream_write`), `:74/:101/:105/:134` (the three init functions).
- **Trigger:** `_stream_grow` stores the doubled capacity to ctx+32 even when `alloc(new_cap)` returns 0 (from `new_cap > ALLOC_MAX` or real exhaustion) and leaves ctx+24 = 0; the buffered write loop then exits (cap grew) and stores through `buf = 0`.
- **Proof:** Pure public API — `stream_decompress_init(FORMAT_GZIP)` then nine honest 256 MiB `stream_write` chunks → SIGSEGV on the 8th when the internal buffer doubling requests 4 GiB; also via the bogus `stream_write(ctx, data, 1<<40)`. Embedded/initrd consumers with a fixed heap hit the same via real pressure at their own cap.
- **Verified fix:** `_stream_grow` returns `-ERR_OOM` and leaves ctx untouched on failure; the write loop propagates it; the three init functions check each alloc and `_sankoch_unlock()` before returning 0 where they hold the lock. Route the 5 allocs through `_sankoch_alloc`.

### LOW

#### L-1 — bzip2 **decode** table-init has the same sentinel bug, shielded only by allocation order
- **Location:** `src/bzip2.cyr:408` (`_bz_alloc_tables`, guards on `_bz_tt`).
- **Severity:** LOW (verified down from a HIGH report). Same shape as M-8, but `_bz_tt` is both the last and largest (7.2 MB) alloc, so a bump-allocator OOM that fails an earlier request also fails `_bz_tt` → guard stays 0 → retry is safe. Reachable only via the one-shot `_sankoch_alloc_set_fail_at` hook or a transient/reordered allocator; **no attacker-controlled public-API trigger.** Latent — becomes real the moment someone reorders the block or swaps in a free-list allocator.
- **Verified fix:** Same `_bz_tables_ready` completion-flag pattern as M-8; land it in the same change so the two halves of an identical defect don't drift.

#### L-2 — Concatenated-gzip ratio-headroom clamp writes exactly 1 byte past the ceiling
- **Location:** `src/gzip.cyr:150-154`.
- **Trigger:** Two concatenated gzip members of 33 zero bytes (66 bytes) with `max_ratio=1` — member 1 emits 66 (== ceiling), the headroom clamps to 1, member 2 emits byte 67 before tripping `ERR_RATIO_LIMIT`. 396 triggering cases in K=8..40000 (the report's "6" undercounted). No OOB (`dp >= dst_cap` fires first) — the extra byte lands inside the caller's buffer.
- **Verified fix:** The auditor's proposed `return ERR_RATIO_LIMIT` on zero headroom is **defective** — it rejects a legal `[member at ceiling][empty trailing member]` stream (485 cases proven, valid per RFC 1952, and neither `cyrius test` nor `cyrius fuzz` catches the regression). The correct fix keeps the ratio clamped to 1 but **starves the member via `member_cap = 0`** and maps the resulting `ERR_BUFFER_TOO_SMALL` back to `ERR_RATIO_LIMIT`: makes the ceiling exact, preserves the empty-trailing-member case, and fixes a tight-buffer error-code slip as a bonus. Add both the K=66 overshoot and the K=63 empty-trailing-member cases to `tests/tcyr/ratio_cap.tcyr`.

#### L-3 — Batch DEFLATE stored-block path missing the `DECOMPRESS_MAX_OUTPUT` guard the streaming path enforces
- **Location:** `src/deflate.cyr:392-397` (non-dict) and `:494-495` (dict).
- **Trigger:** ~17 MiB of `BTYPE=00` stored blocks with `dst_cap ≥ 17 MiB`: batch returns 17,827,157 bytes (past the 16 MiB ceiling) while streaming returns `ERR_OUTPUT_LIMIT`. No OOB (`dp + len > dst_cap` fires first); stored blocks are 1:1 so not a bomb. The real defect is that the `types.cyr:41` "16 MB hard ceiling" invariant isn't invariant and batch/streaming disagree.
- **Verified fix:** `if (dp + len > DECOMPRESS_MAX_OUTPUT) { return 0 - ERR_OUTPUT_LIMIT; }` beside the existing `dst_cap` check at both sites (matches `deflate.cyr:1015`). Note the "tar ladder reasons about ERR_OUTPUT_LIMIT" rationale was refuted (the ladder never touches the DEFLATE path), and the fix makes `TAR_MAX_OUT` dead code for the gzip branch — a peer decision.

#### L-4 — RFC 8878 errata 7297: 4-stream literals with Regenerated_Size < 6 accepted (conformance only)
- **Location:** `src/zstd.cyr:512-518` and `:522`.
- **Trigger:** A Compressed_Literals_Block with Size_Format=01 (4 streams) and Regenerated_Size in 0..5. The fourth-stream size underflows; the negative count short-circuits the decode loop, so **no OOB** — the frame is merely accepted where reference `zstd -dc` rejects it (proven: reference rejects 0..5 as `literals_headerWrong`; sankoch returns them). The affected set is 0..5, not the reported {1,2,5}. No encoder exposure (sankoch only selects 4-stream mode for n>1023).
- **Verified fix:** `if (regen2 < 6) { return 0 - 47; }` before the split, plus a defensive `if (n < 0) return -1` in `_z_huff_decode_stream`. Byte-exact interop preserved. **Note a strictly larger conformance gap found in passing** (worth its own follow-up, not this fix): `_z_huff_decode_stream` validates neither exact bitstream termination nor under-read, so sankoch already accepts a broad class of invalid 4-stream frames that `zstd` rejects (regen=6/8/12 confirmed).

#### L-5 — Testability: 70 allocations bypass the `_sankoch_alloc` fault-injection seam; `fuzz_xz` has no truncation strategy
- **Location:** `src/zstd.cyr` (57 raw `alloc()`), `src/tar.cyr` (8), `src/stream.cyr` (5); `fuzz/fuzz_xz.fcyr:77-156`.
- **Observation:** `_sankoch_alloc_set_fail_at` never fires on zstd/tar/stream, so their OOM paths (M-3, M-8-zstd, M-13) are structurally untestable by the existing sweep — this is *why* zstd scored a deceptive 0/40. The proposed "just route through `_sankoch_alloc`" fix is **not viable as written**: it breaks `[lib.zstd]` self-containment (undefined `_sankoch_alloc` in the standalone profile) and, without accompanying null-checks, turns an injected OOM into a segfault. A viable fix must first add the null-checks (M-8/M-11 territory) and choose a seam that doesn't force lean profiles to pull `runtime.cyr` (e.g. a module-local alias). Separately, `fuzz_xz` mutates only random/byte-flip/round-trip/ratio-cap — never truncation, the one class that reaches M-5; add a `fuzz_xz_truncate` strategy (pairs with M-5's real fix).

### INFO (new)

#### I-1 — `_sankoch_reset_tables()` omits every xz/bzip2/zstd/crc64 lazy global
- **Location:** `src/lib.cyr:73-96`.
- **Observation:** The reset helper the OOM sweep depends on zeroes only crc32/lz77/lz4/huffman/deflate globals. It touches no `_xz_*`, `_xze_*`, `_bz_*`, `_bze_*`, `_z_*`, `_ze_*`, zlib, gzip, or `crc64_table` pointer. So even after widening `_oom_compress_path` to new codecs, a warmed global is never re-nulled and the first-call OOM site never re-triggers — proven: FORMAT_ZSTD/xz sweeps see 0 injected faults land without the reset, >10 with it. Test-infrastructure completeness gap, no runtime effect, no public-API trigger → INFO (both the xz-scoped and bzip2-scoped reports rebased here). The speculative "this is why M-8 shipped undetected" claim is **unproven** — the widened compress-side sweeps are clean; M-8 lives on the *retry-without-reset* path the reset-based sweep can't exercise by construction.
- **Fix:** Extend `_sankoch_reset_tables()` with the xz (`_xz_probs`, `_xze_*`), bzip2 (`_bz_*` × 13, `_bze_*` × 21), zstd, and `crc32bz_table`/`crc64_table` pointers, and add an OOM-then-**retry** phase to `_oom_compress_path` (the retry is what catches the M-8 latch class). Keep the assignments in `lib.cyr` (full-profile-only) so lean profiles are unaffected. The originally-proposed fix listed non-existent `_bz_tables_ready`/`_bze_ready` variables and miscounted the `_bze_*` set — use the sentinel pointers.
