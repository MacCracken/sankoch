## Summary

- **1 HIGH** — DEFLATE stored-block raw-byte copy bypasses the
  bitreader's source-bounds check, allowing a crafted malformed
  stream to read up to 65,535 bytes past the input buffer. Fixed
  in 2.1.3.
- **1 MEDIUM** — DEFLATE dynamic-block parser accepts HLIT field
  encodings 30-31, yielding a literal/length code count of 287 or
  288 (RFC 1951 §3.2.7 caps the count at 286). No exploit path —
  the all_lens buffer has slack — but the stream is spec-invalid.
  Fixed in 2.1.3.
- **2 LOW** — zlib parser doesn't enforce CINFO ≤ 7 (RFC 1950 §2.2);
  gzip parser doesn't reject reserved FLG bits 5-7 (RFC 1952
  §2.3.1.2). Both fixed in 2.1.3.
- **1 INFO** — gzip FHCRC field is skipped without verification.
  RFC 1952 marks the verification as a SHOULD; reference gunzip
  didn't enforce it until 1.5+. Backlogged.
- **0 findings** in the kernel-safe `[lib.core]` profile
  (`src/types.cyr` + `src/xxhash32.cyr` + `src/lz4_decode.cyr`).
  Re-grep for `alloc(` / `sys_*` / `_sankoch_lock` / `mutex_*` in
  `dist/sankoch-core.cyr`: zero hits. The kernel-safe tripwire
  (`programs/core_smoke.cyr`) covers regression.

## HIGH (fixed in 2.1.3)

### HIGH-01: DEFLATE stored-block source bounds bypass

**Files**: `src/deflate.cyr` — `_deflate_decompress_inner` (lines ~358-380)
and `_deflate_decompress_dict_inner` (lines ~441-460).
**RFC reference**: RFC 1951 §3.2.4 (non-compressed blocks).

**Risk**: After parsing BFINAL=1, BTYPE=0 (stored block), the
decompressor reads LEN (16-bit LE) and NLEN (16-bit LE one's
complement of LEN) from the stream, verifies `LEN ^ NLEN == 0xFFFF`,
checks `dp + LEN <= dst_cap`, and then copies LEN raw bytes from the
backing buffer using direct loads:

```cyrius
var data = load64(br);
var bpos = load64(br + 8);
var i = 0;
while (i < len) {
    store8(dst + dp, load8(data + bpos));
    ...
}
```

The direct-load path bypasses `br_read`'s `bpos < dlen` check.
A crafted malformed stream with `LEN > (dlen - bpos)` triggers a
read of up to 65,535 bytes past the source buffer. Effects depend
on memory layout:

- **Information disclosure** — adjacent process memory copies into
  `dst[]` and surfaces through the decompressed output. A caller
  that returns the decompressed bytes to an attacker (e.g. a server
  that decompresses untrusted gzip request bodies) leaks heap
  contents.
- **Process crash** — if the source buffer is at the end of a
  mapped page with no following mapping, the load faults.

**Reachability**: any caller that decompresses untrusted DEFLATE,
zlib, or gzip data is exposed. zlib and gzip wrap DEFLATE through
`_deflate_decompress_inner`, so the same path covers all three
formats. The streaming decompress wrapper (`stream_decompress_*`)
buffers then calls the same inner, also exposed.

**Fix (2.1.3)**: re-assert the bound against the bitreader's backing
length immediately before the copy loop:

```cyrius
if (bpos + len > load64(br + 24)) { return 0 - ERR_CORRUPT_DATA; }
```

Identical fix applied to both inner functions. No effect on valid
streams (the existing test suite continues to pass byte-for-byte).

**Test coverage**: `test_err_deflate_stored_oob` — 5-byte input that
declares LEN=100 with valid NLEN; pre-fix would walk 100 bytes past
the buffer, post-fix returns `-ERR_CORRUPT_DATA`.

**Why didn't fuzz catch it**: `fuzz_deflate.fcyr` round-trip and
malformed-input harnesses bias toward shorter LEN and rarely
combine "valid NLEN" + "LEN > remaining". The harness wasn't
crafted to hit the precise stored-block bound — adding a targeted
malformed-stored-block iteration to the harness is a follow-up
candidate (not blocking 2.1.3).

## MEDIUM (fixed in 2.1.3)

### MED-01: DEFLATE HLIT field accepts spec-invalid encodings 30-31

**File**: `src/deflate.cyr` — `_deflate_read_dynamic` (line ~202).
**RFC reference**: RFC 1951 §3.2.7. "HLIT, # of Literal/Length
codes - 257 (257 - 286)".

**Risk**: HLIT is a 5-bit field encoding values 0..31, with the count
computed as encoded + 257. Valid range per spec: encoded 0..29,
yielding count 257..286. Encoded values 30 and 31 produce counts 287
and 288, which the spec forbids. The pre-2.1.3 parser accepted those:

```cyrius
var hlit = br_read(br, 5);
hlit = hlit + 257;
# (no upper bound check)
```

The downstream `all_lens[4672]` buffer is sized to 584 i64 entries —
plenty of slack to avoid OOB even at 320 entries (HLIT=288 + HDIST=32),
so no buffer overrun. The risk is therefore spec compliance and
attack-surface containment: a 287-entry literal/length tree is
structurally inconsistent with the rest of the decoder, and silently
proceeding through code paths designed for ≤286 invites a future
defect to escalate.

**Fix (2.1.3)**: cap immediately after the +257 adjustment:

```cyrius
if (hlit > 286) { return 0 - ERR_CORRUPT_DATA; }
```

**Note**: HDIST and HCLEN don't share this problem. HDIST count is
encoded+1, range 1..32 — all 5-bit encodings valid per spec. HCLEN
count is encoded+4, range 4..19 — all 4-bit encodings valid. Comments
in the patched code call this out so a future reader doesn't add a
mirror check that's actually a false positive.

**Test coverage**: `test_err_deflate_hlit_overflow` — 1-byte header
with HLIT=30 in the 5-bit field, expects negative error.

## LOW (fixed in 2.1.3)

### LOW-01: zlib CINFO not validated

**File**: `src/zlib.cyr` — `_zlib_decompress_dict_inner` (line ~47).
**RFC reference**: RFC 1950 §2.2. "For CM = 8, CINFO is the base-2
logarithm of the LZ77 window size, minus eight (CINFO=7 indicates a
32K window size). Values of CINFO above 7 are not allowed in this
version of the specification."

**Risk**: CINFO is the high 4 bits of CMF. The parser checked `CM == 8`
(low 4 bits) but didn't bound CINFO. Streams claiming CINFO=8..15
(window 64K..1MB) parsed successfully against sankoch's fixed 32K
window. No exploit — the inner DEFLATE decode treats every distance
relative to its own 32K window regardless of header claims — but the
stream is spec-invalid.

**Fix (2.1.3)**: explicit cap right after the CM check:

```cyrius
if (((cmf >> 4) & 15) > 7) { return 0 - ERR_UNSUPPORTED_FORMAT; }
```

**Test coverage**: `test_err_zlib_cinfo_overflow` — header with
CMF=0x88 (CINFO=8, CM=8) and FLG chosen so the FCHECK `% 31 == 0`
holds, expects negative error.

### LOW-02: gzip reserved FLG bits not rejected

**File**: `src/gzip.cyr` — `_gzip_decompress_member` (line ~33).
**RFC reference**: RFC 1952 §2.3.1.2. "Reserved FLG bits ... must be
zero. If any reserved bit is non-zero, a compliant decompressor must
give an error indicating that the input is not in the gzip format,
or in some way reflects the presence of the unknown bit."

**Risk**: FLG bits 0-4 are FTEXT, FHCRC, FEXTRA, FNAME, FCOMMENT.
Bits 5-7 are reserved and must be zero. The pre-2.1.3 parser checked
the defined bits via masking but never tested whether bits 5-7 were
clear. Same posture as LOW-01 — spec compliance, no known exploit.

**Fix (2.1.3)**: reject after reading FLG:

```cyrius
if ((flg & 224) != 0) { return 0 - ERR_CORRUPT_DATA; }
```

(Mask `0xE0 = 224` covers bits 5-7.)

**Test coverage**: `test_err_gzip_reserved_flg` — 18-byte header
with FLG bit 5 set, expects negative error.

## INFO (documented, backlogged)

### INFO-01: gzip FHCRC value not verified

**File**: `src/gzip.cyr` — `_gzip_decompress_member` (lines ~74-76).
**RFC reference**: RFC 1952 §2.3.1.2. "If FHCRC is set, a CRC16 for
the gzip header is present, immediately before the compressed data."

**Status**: Per-spec a SHOULD-verify, not a MUST. Reference gunzip
historically did not enforce until 1.5; many modern gzip impls
(libdeflate, miniz, Go's `compress/gzip`) skip the CRC16 entirely.

**Cost to fix**: implement CRC16-IBM (polynomial 0xA001) over the
already-parsed header bytes plus a 2-byte read-and-compare. ~30 LoC,
no performance impact (only fires when FHCRC bit is set, which is
rare in practice — `gzip` CLI sets it only with `--rsyncable`).

**Decision**: backlog. Not blocking 2.1.3. If a future consumer
generates FHCRC-bearing streams that mutate in transit, revisit.

## Process notes — what surfaced and how

**Tooling**: this audit was a manual read of the parser surface
(zlib.cyr, gzip.cyr, deflate.cyr's decompress side, bitreader.cyr,
huffman.cyr's decode side). No fuzzer crash drove the HIGH-01 finding;
it surfaced from a deliberate cross-check between the bitreader's
`bpos < dlen` branch (bitreader.cyr:38) and the direct-load uses of
`load64(br)` / `load8(data + bpos)` elsewhere.

**Coverage of the 2.1.2 split**: `src/xxhash32.cyr` and
`src/lz4_decode.cyr` (both new at 2.1.2) reviewed and found clean —
no alloc, no syscalls, no mutex usage. The kernel-safe profile
constraint is therefore preserved at 2.1.3 and the
`programs/core_smoke.cyr` tripwire continues to pass.

**Benchmarks**: pre/post the four fixes show no regression on the
hot path — every patched check sits on a cold or error branch. Bench
deltas across the 25 timed cases land within run-to-run noise
(±5%); none of the inner decode loops were touched.

**Test count**: tcyr suite grew by 4 assertions
(1,028,625 → 1,028,629) — exactly the four new audit-regression
tests. git_object suite unchanged at 346,583. Total at 2.1.3:
**1,375,212** assertions across the two suites.
