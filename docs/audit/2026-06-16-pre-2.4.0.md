## TL;DR

**Zero HIGH / MEDIUM / LOW findings.** Every gate green (build 0 warnings,
lint 0 warnings/file, `cyrfmt --check` clean, `vet` clean, both `.tcyr`
suites + all fuzz harnesses + `core_smoke` + aarch64 cross-build). All 43
SIZE wire-format lines are byte-for-byte identical to the 2.3.4 baseline
— the 2.3.5–2.3.7 work touched decode + allocation paths only, never the
encoder output. Cleared to open 2.4.0.

The headline robustness gain this cycle: the new **OOM fault-injection
sweep** (2.3.7) sweeps a simulated allocation failure across every alloc
offset on each public encode/decode path and asserts a clean result —
its completion is a machine-checked proof of *no crash and no deadlock*.
It already paid for itself by surfacing a pre-existing latent segfault
(unchecked `bw_init` OOM on the batch DEFLATE encoder), now fixed.

## Re-checks (targeted at the new 2.3.x paths)

1. **Source-bounds on the new `*_dec_*` state machines** (mirror of the
   2.1.3 HIGH-01 fix). The streaming gzip FHCRC fold and the
   concatenated-member `AFTER_TRAILER` probe both read `input[cp]` only
   under a `cp < in_len` guard; the header-CRC fold covers exactly
   `[hcf_start, cp)` with `cp ≤ in_len`. **Clean.**

2. **Streaming-LZ4F block-buffer sizing under varied BD** (post-2.3.3).
   The per-frame `block_max` (ctx+96) is derived from the validated
   BD block-max ID (≥4), the block buffer is allocated to that size, and
   `BLOCK_SIZE` rejects `bsv > block_max`. Block-data accumulation and
   the per-block `xxhash32(block_buf, bsv)` both stay within `bsv ≤
   block_max = buffer size`. **In bounds.**

3. **Per-block checksum paths** (2.3.3). Decoder consumes 4 LE bytes
   under the `cp` cursor and validates against the buffered on-wire
   block before emit; batch mirror advances `sp` by 4 with a
   `sp + 4 > src_len` guard. **Clean.**

4. **FDICT dict-scratch match-copy bounds** (post-2.3.6). The distance
   check `distance > dp_match + dict_len → -ERR_MATCH_OUT_OF_RANGE`
   guarantees `src_match = dp_match - distance ≥ -dict_len`, so a
   negative logical offset reads `dict[dict_len + spos]` with
   `dict_len + spos ∈ [0, dict_len)`; once `spos ≥ 0` it reads
   already-written `dst` (`spos < dp_match`). Both the dict and dst
   reads are in bounds; the write is gated by the existing
   `dp + length > dst_cap` check. **No OOB.**

5. **Bit-accumulator overpull rewind** (zlib/gzip). Unchanged 2.3.0
   mechanism; the concatenated-gzip per-member `deflate_dec_reset`
   zeroes `hold`/`bits` so each member starts byte-aligned. **Clean.**

6. **Alloc-fail propagation paths** (post-2.3.7). The ~33 lazy-global
   allocs route through `_sankoch_alloc` and propagate `ERR_OOM` (batch)
   / null + unlock (ctx). The OOM sweep exercises every offset on
   DEFLATE/GZIP/LZ4 compress + GZIP/DEFLATE decompress; it completes,
   which proves no path leaves the mutex held (a held mutex would
   deadlock the next iteration's `_sankoch_lock`). **Validated.**

## INFO ledger

- **INFO-01** (gzip FHCRC validation) — **CLOSED at 2.3.5.**
- **INFO-A** (lazy-global alloc-fail) — **CLOSED at 2.3.7.**
- **INFO-B** — the *batch* `*_decompress_dict` paths still require
  `dst_cap ≥ dict_len` (the dict is staged in `dst`). The 2.3.6
  *streaming* FDICT path removed this for the streaming variant (dict
  in scratch), but the batch constraint stands. Already enforced at
  runtime; docstring-polish item. **Carried.**
- **INFO-C** — aarch64 LZ77 / FDICT match-copy use unaligned `load64`.
  ARMv6+ permits it; some implementations pay a cycle penalty. aarch64
  cross-build is green. **Carried** (revisit only if aarch64 perf
  benchmarks surface it).
- **INFO-D** (new, minor) — on a *retried* OOM, partially-allocated
  lazy tables orphan their bump-allocated memory (the `_sankoch_alloc`
  arena does not free). OOM-path only; the realistic OOM victim aborts
  rather than retries. Flagged for completeness.

## External research

RFC errata sweep (RFC 1950 / 1951 / 1952) and reference `zlib` / `lz4` /
`gzip` behavior since the 2.2.7-era audit surfaced nothing that changes
sankoch's paths. The one correction this cycle was sankoch-internal: the
roadmap's FHCRC item mis-stated the checksum as CRC-16-IBM; RFC 1952
§2.3.1.2 specifies low-16-of-CRC-32, which 2.3.5 implemented and verified
against reference `gunzip`.
