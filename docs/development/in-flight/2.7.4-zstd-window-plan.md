# Sankoch 2.7.4 — zstd Encoder Cross-Block Match Window (FINAL PLAN)

## 1. Overview, Option Choice, Expected Gain

**What ships.** The zstd encoder today emits data in 128 KiB blocks and resets its hash chain *per block* with *block-relative* positions, so no sequence can reference a match in a prior block. 2.7.4 makes a block's sequences reference matches in prior blocks by lifting the parse to **frame-global coordinates** with a **persistent, window-bounded hash chain**, growing the effective match window from the 128 KiB per-block cap to a swept **256 KiB–4 MiB** frame-global window (default **2 MiB**). The entire change is confined to the parse layer.

**Nothing about framing changes.** `_ze_frame_header` (src/zstd.cyr:1075) already emits `single_segment=1` (`(1<<5)`) with Frame_Content_Size, so `Window_Size == full content` and every cross-block offset is spec-legal for reference `zstd -d` with no header, windowLog, or offset-encoding change. Offset codes 0..31 already span multi-GB; a 2 MiB offset is code ~21.

**The dominant lever is repcodes, not the literal-match window.** `_ze_ro1/2/3` already carry across blocks, but were *unreachable* cross-block: the block-relative guard `ro <= pos` failed for the first ~`ro` positions of every block. With global positions, `ro <= global_pos` lights up cross-block repcodes, and **repcodes are never window-bounded** (always valid under single_segment). For the record fixture (records every ~89 B), cross-block repcodes carry most of the win; the widened literal-match window closes the remainder.

**Expected gain.** Record-data **L9: 227,721 B → decisively toward `zstd -19`'s 131,820 B**; **L6: 249,873 B → toward `zstd -6`'s 218,662 B**. Single-block inputs (≤128 KiB, incl. source/text corpus) stay **byte-identical** to 2.7.3. The analogue is xz 2.7.2 (dictionary/window growth: +7% gap → +0.2%).

**Chosen approach: Option B** — keep the per-block emit loop; give each block's parse the global `src` base, a persistent frame-global chain, a windowed `_ze_prev`, and global offsets. Matches are **clamped to end at the block boundary** (a match may *reference* a prior block, but its copied output bytes stay within the current block — exactly RFC sequence-execution semantics).

*Why not Option A* (parse whole input once → global sequence list → split into blocks): a match straddling a block boundary must be split into two sequences with recomputed literal accounting and per-split repcode state, and it forfeits 2.7.3's per-block best-of (greedy vs optimal) unless the whole input is parsed twice and both split. Option B changes nothing about block framing, per-block FSE stats, per-block literal buffers, or the best-of. The repcode/offset engine (`_ze_offval`, `_ze_pr_update`, `_zo_newrep`, `_zo_ofbase_of`) is already distance-based and RFC-correct, so global distances flow through the emitter with **zero arithmetic change** — the only edits are coordinate globalization, chain lifetime, and reach guards.

### 2.5 Hash reset moves to frame start

Delete the head-reset loops from the top of **both** parses (**1690** and **2038**). In `_ze_encode` (2832), before the block loop and **only after** a successful `_ze_lz_alloc()` (check `_ze_oom`; on failure fall through to the existing Raw/RLE store path), compute the window and reset head once:

```
if (_ze_lz_alloc() >= 0 && _ze_oom == 0) {
    var e = _z_flog2(src_len);
    if ((1 << e) < src_len) { e = e + 1; }      # pow2_ceil(src_len)
    var wsize = 1 << e;
    if (wsize > _ze_maxwin) { wsize = _ze_maxwin; }
    if (wsize < 262144)     { wsize = 262144; }  # FIX-B2 floor: strictly > BLKMAX
    _ze_wsize = wsize; _ze_wmask = wsize - 1;
    var h = 0;
    while (h < (1 << 16)) { store64(_ze_head + h * 8, 0 - 1); h = h + 1; }
}
```

**FIX-B2 (was razor-thin).** The window floor is **`262144` (2×BLKMAX = 1<<18)**, not `131072`. This puts a full block of headroom between a block's slot range and its window-aliased neighbor, decoupling the "distinct-slots-per-block" and "chain_fill overwrites all scribbles" invariants from the exact `BLKMAX == 131072 == floor` power-of-two coincidence. Document `wsize_floor > BLKMAX` next to the `_ze_maxwin` knob. Single-block inputs (`src_len ≤ 131072`) have no cross-block chain and are unaffected.

### 2.8 Chain lifetime — the one genuinely new mechanism

```
fn _ze_chain_snapshot()  # copy 64K-bucket head -> _ze_head_save (512 KiB)
fn _ze_chain_restore()   # copy _ze_head_save -> head
fn _ze_chain_fill(g, bstart, bend, glen)
    var p = bstart; while (p < bend) { _ze_insert(g, p, glen); p = p + 1; }
```

`_ze_chain_fill` is the **single canonical, parse-independent** chain advance for a block — identical regardless of which encoding or which parse won.

**`_ze_try_seq_block(g, bstart, bend)` restructured — FIX-A1 (blocker: unconditional restore).** The "best-of leaves identical chain state" guarantee requires `_ze_chain_restore()` on **every** post-snapshot exit. Structure it so:
1. Pre-snapshot guards run first (`n < 16` at 2802, `_ze_huff_alloc` fail at 2803 — both return **before** any snapshot/parse; no restore needed).
2. `_ze_chain_snapshot()` once, at the top, **after** those guards.
3. Every path that follows a parse — including the **L1–6 greedy-only** `return _ze_try_seq_one(...)` at 2804, and both greedy-wins / optimal-wins returns — calls `_ze_chain_restore()` **unconditionally before returning**.
4. For L7–9: run greedy, `_ze_chain_restore()` before the optimal attempt (both attempts see the identical persistent chain), then restore at exit.

If any post-snapshot return skips the restore, the parse's block-N head insertions survive, and `_ze_chain_fill` then inserts the same positions a **second time**, producing forward/cyclic links — benign for correctness (`off <= 0` breaks forward links, `depth < chain_max` bounds iteration, byte-verify rejects bad offsets) but it silently corrupts the chain, loses exactly the cross-block ratio 2.7.4 exists to capture, and makes the chain winner-dependent (breaking the determinism the design relies on). **Debug assertion:** at each `_ze_chain_fill` entry, `head == head_save` (or total chain inserts across the frame `== glen - 3`).

**`_ze_encode` block loop (2853–2867).** Pass **global** coords: `_ze_try_seq_block(src, pos, pos + chunk)` (not `src + pos, chunk`). After emitting **each** non-empty block — RLE, Compressed-seq, Compressed-huff, Raw alike (a discarded/fallback block's bytes are still in the decoder window and a later block may match them) — call `_ze_chain_fill(src, pos, pos + chunk, src_len)`. This advances the persistent chain by exactly the block's positions in increasing order, identical regardless of encoding or winning parse.

**Why prev needs no restore (bounded memory/time).** Parses scribble `_ze_prev[p & _ze_wmask]` for block-N positions, aliasing prior slots `[bstart-W, bend-W)`. But (a) find/getmatches **byte-verify** every candidate, so a corrupted link only shortens/drops a match — never a bad offset; (b) the `off < _ze_wsize` bound rejects any candidate a scribble sends out-of-window; (c) after `_ze_chain_fill`, all in-window links for subsequent blocks are correct, and the scribbled prior slots are all at distance ≥ W from every future search position (≥ `bend`) → out-of-window → benign. With the **FIX-B2 floor `wsize > BLKMAX`**, a block's live slots are pairwise-distinct and never alias its own boundary. So only the **512 KiB head** is snapshot/restored; the multi-MB prev is not.

## 3. Decodability Argument (reference `zstd -d` 1.5.7)

Four invariants, none touched by this change:

1. **Single-segment framing.** `_ze_frame_header` (1069–1081) keeps `(1<<5)` single_segment with FCS present ⇒ RFC 8878 §3.1.1.1.2: `Window_Size == Frame_Content_Size == full content`. Every decoded byte is a legal back-reference target; any cross-block offset is in-bounds.
2. **Offset ≤ content.** Offsets are global distances `global_pos - candidate`, `candidate ≥ frame_start = 0` (rep guard `ro <= pos`, find guard `off > 0`) ⇒ `offset ≤ current_output_pos ≤ content < Window_Size` (§3.1.1.4 satisfied). Match length clamps at `bend`, so copied output never crosses into an undecoded block.
3. **Offset encoding ≤ 31.** `_z_flog2(offset + 3)` at a 2 MiB window ⇒ offset code ~21 ≤ 31 (decoder validates `ofcode <= 31` at ~710; OF freq/predefined tables cover codes 0..28, safe to a 256 MiB window). The `+3` keeps every literal Offset_Value ≥ 4, never colliding with repeat codes 1/2/3.
4. **Repcode rotation.** `_ze_ro1/2/3` per-frame, reset only at frame start, advanced only by committed blocks in sequence order via `_ze_offval` (== the decoder's `_z_resolve_offset`), including the `LL==0` remap — carried intact across boundaries.

**FIX-DEC1 (scoped claim, pre-existing).** Single-segment framing means `Window_Size == content`, so a payload **≥ 128 MiB** (`1<<27`) trips reference `zstd -d`'s default windowLog-27 limit at **frame-header parse time** (`frameParameter_windowTooLarge`), before any offset is examined — independent of how small the actual offsets are. This is **pre-existing** (2.7.3 already emits single_segment with full FCS) and **orthogonal** to window growth. Keep the CHANGELOG/state.md claim **scoped**: *"inputs < 128 MiB decode under plain `zstd -d`."* Do **not** upgrade it to an unqualified "every stream decodes." A true universal fix (emit a Window_Descriptor with windowLog ≤ 27 when `src_len >= 1<<27`) is a separate, out-of-scope framing change — not a 2.7.4 blocker.

**Critical gate.** sankoch's own decoder retains the full output as its window and will **not** catch a malformed global offset. **Every** verification must round-trip through reference `zstd -d`.

## 5. Residual Open Questions / Risks

- **Window default (bite 4).** Cross-block repcodes have unlimited reach and record data is repcode-dominated, so a modest window (256–512 KiB) may capture most of the record win; the window mainly helps non-repcode long-range **literal** matches on less-regular multi-MB source. Recommend 2^21 (2 MiB) pending the sweep; 2^20 (1 MiB) fallback.
- **Persistent prev memory.** `_ze_prev` at `_ze_maxwin*8` (16 MiB at 2 MiB) is a one-time global reused across calls. zstd encode is full-profile only (not `[lib.core]`), so acceptable — but over-allocates for tiny inputs. Grow-only per-call sizing is the mitigation (decide in bite 4).
- **Prev-scribble in the best-of.** Chosen: head-restore-only between attempts, relying on byte-verify + window bound for correctness, accepting a minor optimal-attempt ratio imperfection (greedy's residual prev writes on window-edge-aliased slots). Bite 3 should measure whether a full window-sized prev-restore buys enough extra L9 ratio to justify the memory/time.
- **OF-code ceiling.** Predefined OF table = 29 symbols (0..28); `_zo_offreq` sized 36, `_ze_phist` sized 64 — all safe to a 256 MiB window (max ofcode ~28). Revisit only if `_ze_maxwin` is ever raised above ~2^28. Out of scope at ≤ 4 MiB.
- **Boundary-position insertion off-by-one.** `_ze_insert` uses `glen`, so block-boundary positions insert using next-block context (better cross-block matches, and correct — those positions are valid decoded output). Confirm no off-by-one at the final 3 frame positions (`pos+4 > glen` skips them, matching the old `pos+4 > n`).
- **≥128 MiB inputs (FIX-DEC1).** Single-segment framing ⇒ `Window_Size == content`, so a ≥128 MiB payload trips `zstd -d`'s default windowLog-27 limit at header-parse time. Pre-existing, orthogonal to window growth. Keep the CHANGELOG/state.md decodability claim scoped to `<128 MiB`; a universal fix (Window_Descriptor with windowLog ≤ 27 for oversized inputs) is a separate framing change, out of scope for 2.7.4.
