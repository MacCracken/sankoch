# 2.7.4 — zstd cross-block match window (ratio/memory sweep)

**Date**: 2026-07-21 · **Machine**: x86_64 linux · **Toolchain**: Cyrius 6.4.69 ·
**Reference**: zstd-utils 1.5.7 · **Prior**: [`2026-07-20-2.7.0-baseline.md`](2026-07-20-2.7.0-baseline.md)

2.7.4 lets a zstd block's sequences reference matches in **prior blocks**, growing the
effective match window from the 128 KiB per-block cap to a frame-global window. sankoch's
zstd parses each 128 KiB block in isolation (per-block hash reset, block-relative positions),
so before 2.7.4 no match could cross a block boundary — the real limit was the *block*, not
the `_ze_prev` chain size. The fix restructures both parses (greedy + DP-optimal, levels 7–9)
to **frame-global coordinates** with a persistent, window-bounded hash chain, reset once per
frame and advanced canonically per block. No frame-header or offset-encoding change is needed:
the encoder emits **single-segment frames** (`Window_Size == Frame_Content_Size`), so reference
`zstd -d` already accepts any distance up to the content size, and offset codes 0–31 span
multi-GB. The dominant lever turned out to be **cross-block repcodes** — they already carried
across blocks but were unreachable because the block-relative `ro <= pos` guard failed at each
block's start; global positions unlock them (and repcodes are never window-bounded under
single-segment).

## Window sweep — `_ze_maxwin` (compressed bytes, level 9)

Fixtures: `records` = 1.78 MB CSV-like log lines (records every ~89 B); `bigrec` = 4.29 MB of
the same with more fields; `src` = 623 KB concatenated `src/*.cyr`. Reference: `zstd -19`.
`_ze_prev` = `_ze_maxwin × 8` (a one-time, encode-only, grow-persistent allocation).

| window | records | bigrec | src | `_ze_prev` | records vs `zstd -19` |
|-------:|--------:|-------:|----:|-----------:|----------------------:|
| 2.7.3 (128 KiB block) | 227,721 | — | 149,200 | 1 MiB | +72.8 % |
| 256 KiB | 155,452 | 284,005 | 136,048 | 2 MiB | +18.0 % |
| **512 KiB (shipped)** | **126,374** | **278,528** | 133,656 | **4 MiB** | **−4.1 % (beats it)** |
| 1 MiB | 127,176 | 285,069 | 133,590 | 8 MiB | −3.5 % |
| 2 MiB | 125,886 | 281,250 | 133,590 | 16 MiB | −4.5 % |
| 4 MiB | 125,886 | 266,918 | 133,590 | 32 MiB | −4.5 % |
| `zstd -19` | 131,820 | 312,714 | — | — | — |

**Result.** With a cross-block window sankoch's zstd L9 now **beats `zstd -19`** on record data
(and on `bigrec` at every window size — sankoch 267–285 K vs zstd's 313 K). The ratio is
non-monotonic in the window size (the DP/window interaction is noisy — 1 MiB is slightly worse
than 512 KiB on records and bigrec), and memory scales linearly with the window.

**512 KiB is the shipped default** (`_ze_maxwin = 524288`, `_ze_prev` = 4 MiB): it already
beats `zstd -19` on both record fixtures, is competitive with (or better than) larger windows,
and costs ¼ the memory of a 2 MiB window. `src` plateaus at 1 MiB (512 KiB is within 66 bytes
of it — negligible). Larger windows buy only marginal gains on very-large record data (`bigrec`
4 MiB = 267 K vs 512 KiB = 279 K, −4 %) at 8× the memory — raise `_ze_maxwin` (a one-line
change) if a record-heavy multi-MB consumer surfaces.

Single-block inputs (≤128 KiB, incl. the whole source/text corpus and the `bench` zstd fixtures)
stay **byte-identical** to 2.7.3 — the global parse with `bstart = 0` reduces exactly to the old
block-relative parse. Every fixture (records / bigrec / src / large) round-trips through reference
`zstd -d`; the full suite (incl. the OOM fault-injection sweep), zstd fuzz, and encode-smoke are
all green.
