# Sankoch 2.3.4 — CRC-32 slice-by-8 throughput

**Date:** 2026-06-16
**Toolchain:** Cyrius 6.2.15 (manifest-pin)
**Hardware:** x86_64 Linux 7.0.11-arch1-1
**Bundle:** dist/sankoch.cyr (6388 lines)
**Purpose:** Before/after for the 2.3.4 CRC-32 slice-by-8 rewrite. The
old CRC-32 was a serial byte-at-a-time table fold (8× unrolled, but each
byte dependent on the previous through `crc`). Slice-by-8 folds 8 bytes
per iteration via one little-endian `load64` + eight parallel table
lookups. **Output is wire-identical** — every gzip CRC and every SIZE
line is unchanged; this is a pure throughput change.

`cyrius bench tests/bcyr/sankoch.bcyr`. The 4KB case has high run-to-run
variance (small buffer, 100 iters); the 1KB (500 iters) and the new
256K (200 iters) steady-state numbers are the reliable indicators.

---

## CRC-32 (before → after)

| Op                | len    | baseline ns/op | 2.3.4 ns/op | speedup |
|-------------------|--------|---------------:|------------:|--------:|
| crc32   1KB text  | 1024   |          2,951 |       1,370 |  2.15×  |
| crc32   4KB text  | 4096   |         11,374 |     ~6,500* |  ~1.75× |
| crc32   256K text | 262144 |       (new)    |    ~345,000 |  ~2.1×† |

\* 4KB is noisy (±1.5k between runs); directional only.
† vs baseline per-byte cost (1KB baseline ≈ 2.88 ns/byte; 256K steady-state ≈ 1.32 ns/byte).

### Cross-check vs Adler-32 (256K steady-state)

| Op                | len    | ns/op   |
|-------------------|--------|--------:|
| adler32 256K text | 262144 | 394,063 |
| crc32   256K text | 262144 | 345,233 |

Before 2.3.4, CRC-32 ran ~1.5× **slower** than Adler-32 (11.4k vs 7.4k
at 4KB). After slice-by-8, CRC-32 is **faster** than Adler-32 at steady
state — gzip's checksum is no longer the throughput laggard.

## Wire-format

All 43 SIZE lines byte-for-byte unchanged from 2.3.3. CRC output
identical (gated by the gzip round-trip suites + fuzz). No format or API
change — 2.3.4 is a pure performance + toolchain-pin release.

## Not adopted: `good_match` chain-walk early-exit

The roadmap's second 2.3.4 candidate (zlib-style `good_match`: cut chain
probes once a long-enough match is found). Implemented and measured:
on every benchmarked text input it was a **no-op** — SIZE lines
unchanged *and* throughput unchanged (within noise), reproducing the
prior revert ("L6 chain depth 64 too shallow to bite"). The deeper
reason it can't ship under 2.3.4's wire-identical mandate: it's a
speed/ratio tradeoff — on inputs shallow enough to leave output
unchanged it yields no speedup, and on inputs deep enough to speed up it
*changes the selected matches* and breaks the SIZE gate. No regime is
both wire-safe and faster, so it was dropped (roadmap option c).
PCLMULQDQ CRC-32 stays deferred — x86-only (the aarch64 cross-build gate
needs a PMULL path or scalar fallback) and hand-assembled-bytes risk; the
portable slice-by-8 already lifts CRC-32 off the hot path.
