# 2.8.4 — Brotli encoder baseline + cyrius 6.7.10

**Date**: 2026-10-13 · **Machine**: x86_64 linux (Ryzen 7 5800H) · **Toolchain**: Cyrius 6.7.10 ·
**Prior doc**: [`2026-09-16-2.8.0-brotli.md`](2026-09-16-2.8.0-brotli.md)

2.8.4 moves the pin 6.7.5 → 6.7.10 and adds a Brotli encoder (RFC 7932, no static dictionary). No
other encoder changes. This file records the encoder's first baseline, its ratio against the
reference `brotli` 1.2.0 at matching qualities, and the measurements behind three design choices.

## How to read this file

`ns/op` and MB/s are machine-local (one `cyrius bench tests/bcyr/sankoch.bcyr` run on an otherwise
idle desktop); compare them run to run on one machine, not across machines. MB/s for an encode row
is **input** bytes per second. Sizes are exact and reproducible, apart from the fixtures marked
*regenerated*, which `scripts/brotli-encode-smoke.sh` rebuilds from the working tree (`source` is
`cat src/*.cyr`, `elf` is `build/sankoch`, `mixed` includes `/dev/urandom`). The figures below use one
frozen copy of those fixtures.

## SIZE: 47 rows, unchanged

All 47 `SIZE` rows are identical to 2.8.3's, both after the pin move alone (cyrius 6.7.10, no source
change) and with the encoder in the tree. The Brotli encoder adds no SIZE row: its output is not
frozen yet (roadmap), so its lines are informational, like the xz / bzip2 / zstd encoders'.

The ladder is monotone on the general-purpose fixtures. On record-structured data it is not: a
deeper bucket or the 16-entry distance cache lets google/brotli's backward-reference score prefer a
longer, farther match over a cheap repeat distance (`records` is smallest at q0–2, `json` at q3).
That is the score heuristic's limit, and the fix is a priced or optimal parse (roadmap), not a knob.

## Measurements behind the design

**The lazy step is the largest single lever.** At bucket depth 2 (4 entries), adding google/brotli's
one-to-four-step lazy match: `json` 15,435 → 11,157 (−27.7 %), `source` 217,778 → 209,147 (−4.0 %),
`numbers` 15,606 → 13,458 (−13.8 %), in about 1.25× the time. It is on from quality 3.

**Two distance-cache candidates are too few.** Checking only the last two distances at quality 1
made `numbers` 22,909 B where four give 15,619 (+46.7 %). Every quality checks at least four.

**Context modeling is chosen by exact cost.** Literal contexts are clustered by a Shannon-plus-
description estimate, which overfits sparse histograms. The `elf` fixture cut into chunks and coded
at quality 5 with the estimate deciding:

| Chunk | one tree | estimate decides | exact cost decides |
|---:|---:|---:|---:|
| 4 KiB (`elf`) | 75,314 | 75,817 (+0.7 %) | 75,314 |
| 8 KiB (`elf`) | 64,566 | 66,218 (+2.6 %) | 64,566 |
| 16 KiB (`elf`) | 58,328 | 59,265 (+1.6 %) | 58,328 |
| 4 KiB (`source`) | 294,514 | 291,561 | 291,139 (−1.1 %) |
| 16 KiB (`source`) | 245,658 | 238,974 | 238,974 (−2.7 %) |

With the exact comparison (context map + every tree written to a scratch stream, plus Σ count ×
length) context modeling never costs literal bits. Below 1,024 literals it is skipped: on 1 KiB
chunks of `source` it gained 0.015 % (377,724 → 377,667 B) for 2.1× the encode time (146 → 309 ms).

**Incompressible meta-blocks are stored without modeling them.** google/brotli's `ShouldCompress`
(fewer than one copy per 256 bytes, ≥ 99 % literals, ≥ 7.92 bits of entropy per literal) stores the
block straight away: `brotli c rand 4K q6` went 9,580,673 → 82,517 ns (116×). Before it, the
encoder clustered 64 near-uniform context histograms under two modes to then store the block anyway.

## Memory

A 2.15 MiB workspace slab + 128 KiB of hash counters + a bucket table of 128 KiB × 2^bb (bb = 0..6
by quality): about 2.4 MiB at quality 0, 6.3 MiB at 6 (the default), 10.3 MiB at 9–11. Allocated on
first use, memoized, grown when a later call needs a larger table, cleared by `alloc_reset()`
detection ([architecture 005](../architecture/005-brotli-encoder-invariants.md)).
