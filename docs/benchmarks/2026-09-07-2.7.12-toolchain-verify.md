# 2.7.12 — toolchain re-verification baseline (cyrius 6.6.0, 2026-09-07 build)

**Date**: 2026-09-07 · **Machine**: x86_64 linux · **Toolchain**: Cyrius 6.6.0 ·
**Prior full SIZE table**: [`2026-06-16-pre-2.4.0.md`](2026-06-16-pre-2.4.0.md) ·
**Prior doc**: [`2026-08-23-2.7.9-sync-flush.md`](2026-08-23-2.7.9-sync-flush.md)

2.7.12 changes no source. This run exists to answer one question: after the 6.6.0
toolchain binaries were rebuilt in place on 2026-09-07, does the tree still emit
the same bytes? It does.

## How to read this file

**Ratios are the signal; timings are not.** Every `SIZE` row is a deterministic
property of the encoders and is directly comparable against any prior benchmark
doc here. The `ns/op` figures are a machine-local baseline from a single unpinned
run on an otherwise-loaded desktop — recorded so a future regression has
something to diff against, but not a cross-release throughput claim. Nothing in
this release should be read as a performance result.

## The primary evidence is the bundle diff, not this table

The strongest statement about 2.7.12 comes from outside this file: each of the
ten regenerated `dist/` bundles diffs **empty** against its 2.7.11 predecessor
once the `# Version:` header line is excluded. There is no 2.7.11 SIZE table to
compare against — 2.7.9 through 2.7.11 shipped focused benchmark docs or none —
so the size table below is validated against the last *full* table instead,
`2026-06-16-pre-2.4.0.md`.

| | Rows |
|---|---:|

| **New fixtures** since pre-2.4.0 (zstd) | 4 |
| **Total this run** | **47** |

The three changed rows are not drift — they are exactly the rows 2.7.9's
fixed-vs-dynamic block chooser was expected to improve, and no others:

| Fixture | pre-2.4.0 | 2.7.12 | Delta |
|---|---:|---:|---:|
| `deflate6_text_1K` | 58 | 55 | -5.2 % |
| `zlib6_text_1K`    | 64 | 61 | -4.7 % |
| `gzip6_text_1K`    | 76 | 73 | -3.9 % |

This independently corroborates the 2.7.9 CHANGELOG claim of "3 of 43 batch SIZE
rows improved, 40 unchanged" — that claim was made from a run never committed as
a full table, and this is the first full table since. The four new rows
(`zstd6_text_4K`, `zstd6_text_64K`, `zstd6_text_256K`, `zstd6_rec_256K`) are
fixtures added with the zstd encoder in 2.5.5; nothing was dropped.

Representative ratios on the 4 KB text corpus: LZ4 71 · DEFLATE L1 80 ·
DEFLATE L6/L9 71 · zlib 77 · gzip 89 · xz 136 · bzip2 141.

The small-input inversion there is expected rather than a defect: xz and bzip2
carry far larger container headers than DEFLATE, so on a 4 KB input framing
dominates. Their advantage shows on the larger fixtures — zstd L6 takes the
256 KB text fixture to **80** bytes against DEFLATE L6's **820**.
