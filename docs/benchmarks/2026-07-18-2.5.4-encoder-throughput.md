# 2.5.4 — xz / bzip2 encoder throughput (before / after)

**Date**: 2026-07-18 · **Machine**: x86_64 linux · **Toolchain**: Cyrius 6.4.66 ·
**Harness**: `cyrius bench tests/bcyr/sankoch.bcyr` (encode sections, 10 iters/line)

All wins are **output-byte-identical** — verified by a 40-input fingerprint
battery (xz + bzip2 × 4 sizes × 5 input shapes: each compressed stream's
length + CRC-32 unchanged), the full tcyr suite (round-trip), and the
`fuzz_xz` / `fuzz_bzip2` encode→decode harnesses. The `out=` (compressed
size) columns are identical before and after, confirming the encoders emit
the same bytes — only faster.

## What changed (all output-preserving)

**xz — the headline.** The optimal-parse block DP (`_xze_dp_fill`) did
O(n × MATCH_MAX) work on repetitive input (~5.5M inner relaxes per 4 KB of
zeros; ~2M for text), which is why repetitive input was ~60× slower than
random (random has almost no matches, so the inner loops never run).

1. **Hoisted `_xze_price_dist` out of the normal-match length loop.** The
   distance price depends on length only via `len_state = min(len-2, 3)`, so
   for a fixed match distance it has ≤ 3 distinct values yet was recomputed
   once per length (~271×/match on long matches). Precompute the 3 values per
   match; index by `min(l-2, 3)`. Byte-identical (`np` is the same i64).
   → text 119.4M → 39.0M (3.06×).
2. **Inlined `_xze_relax` at the two hot length loops** (rep + normal),
   hoisting the loop-invariant state/rep-set/kind/dist args so the common
   non-improving case is just a load+compare instead of a 10-argument call.
   Fields stored are identical. → text 39.0M → 24.0M; zeros 91.6M → 54.3M.
3. **Match-finder `best` pre-check** in `_xze_get_matches`: a candidate can
   only be recorded if it matches at index `best`, so skip the full byte-scan
   when `src[chain+best] != src[pos+best]`. Same matches recorded. (Small on
   this corpus — the DP relaxes dominate, not the finder — but a large win on
   deep-chain corpora.)

**bzip2 — modest (it was already ~35× faster than pre-2.5.4 xz).** The
random worst case is *not* BWT-bound (random ranks resolve in ~2–3 doublings);
the cost is the MTF + multi-table Huffman.

4. **`% n` → conditional subtract** in the BWT prefix-doubling sort
   (`_bze_csort`, rank reassignment, last-column build). `idx, k < n` so the
   sum is `< 2n` → one subtract replaces the division. Output-identical.
5. **Scalarized the 6-group cost accumulator** in `_bze_send_mtf` (the hot
   random-case Huffman-group loop): hold the 6 running costs in locals to drop
   the per-symbol `cost[]` load+store. Same sums, same tie-break → identical
   selectors. → rand 3.65M → 3.45M (~5%).

Neither encoder is in the wire-format SIZE gate, so this is pure speed work;
per the "numbers don't lie" rule the before/after ns/op are recorded above.
